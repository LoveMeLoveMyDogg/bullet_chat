# P0：macOS 兼容修复计划（含 Windows 回归保障）

## 背景（已实测确认）
- macOS 上 `fs.watch` recursive 的**所有事件都是 `rename`**（FSEvents 映射），修改/删除也报 rename → 当前 `classifyEntry` 把"修改"误判为"新建"；FSEvents 还会对监视根目录自身发 `change` 事件（filename=根目录名、路径不存在 → 误判"删除"）
- `listFixedDrives()` 只枚举 `A:\`~`Z:\`，macOS 返回空数组 → 文件监控全部失效
- `npm test` 在 macOS 挂死：3 个测试失败（Windows 假设）+ 失败路径不清理 fs.watch 句柄 → 进程永不退出

## Windows 回归保障策略（核心原则）
1. **所有平台差异收敛在 `process.platform` 分支点**，Windows 分支保持原逻辑一字不动
2. `classifyEntry` 重写后，Windows 判定路径与旧版**结果等价**：`eventType === 'change'` 信号原样保留（Windows 修改事件仍走 change）；rename 事件行为与旧代码一致（stat 存在→create / 不存在→delete）；mtime 比较仅是 macOS 场景（全 rename）下的附加信号
3. 根目录元数据事件跳过逻辑在 Windows 上**永不触发**（条件组合不可能出现，惰性）
4. 交付时附 Windows 验证清单，由你在 Win 机器上执行确认

## 改动清单

### 1. `src/main/fileWatcher.js` — 核心重写
- **`classifyEntry(root, full, eventType, seen = new Map())` 改为 stat + mtime 分类**：
  - stat 失败 → `delete`（从 seen 移除）；stat 成功且 `basename(full) === basename(root)` 的根目录元数据事件 → 返回 `null`（回调跳过）
  - stat 成功：`prev = seen.get(full)`，更新 mtime；`eventType === 'change' || (prev !== undefined && prev !== mtimeMs)` → `change`；否则 → `create`
  - `drive`：仅 Windows 取 `root.slice(0, 2)`，macOS 为 `''`
- **新增 `listWatchRoots()`**：win32 → 原 `listFixedDrives()`；darwin → 家目录 + `/Volumes` 非隐藏挂载点（realpath 排除启动盘 `'/'` 防重复监听）
- `FileWatcher`：`this.seenMtimes`（Map，上限 20000 超出 clear）传入两处回调；构造默认 `drives = listWatchRoots()`；entry 为 null 时跳过
- 导出 `listWatchRoots`

### 2. `src/main/main.js`
